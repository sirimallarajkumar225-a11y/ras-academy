Linux Hardware Error Diagnostics

A practical, evidence-first approach to understanding server hardware error reports on Linux. Examples are illustrative; commands and availability vary by distribution, kernel, hardware and configuration.

Start with the scope and evidence

Before investigating, document the system identity, kernel and software context, workload, time window, impact and what triggered the investigation. Use authorized, read-only collection wherever possible. Keep original records and note time-zone differences.

Review system messages

On systems using systemd, journal records can help establish event context. For example, journalctl -k displays kernel messages, while journalctl --since "1 hour ago" filters journal entries by time. Syntax, permissions and retention vary. Avoid clearing logs or changing settings during initial evidence collection.

Where available and appropriate, tools such as rasdaemon can record or report hardware-related RAS events. Availability, configuration and support differ by platform. Consult the distribution documentation and tool help before relying on its output.

Investigate by reporting subsystem

Memory and ECC

Correlate memory-related records with available topology, event location validity, trend and platform management evidence. A counter or single event alone is not proof of a failing component. Read the ECC memory errors guide.

CPU machine-check records

Preserve the original record and identify which fields are valid. Interpret classifications using applicable architecture and platform documentation. Read the CPU MCA guide.

PCI Express AER

Review reporting source, event category and context; correlate with related device and system records without assuming a root cause. Read the PCIe AER guide.

Correlate before concluding

  1. Normalize timestamps and identify uncertainty.
  2. Compare event records from distinct reporting sources without conflating them.
  3. Establish whether the event repeats, changes or coincides with workload or service impact.
  4. Separate confirmed observations from hypotheses.
  5. Use supported diagnostic and service procedures to determine next steps.

Evidence checklist

  • System and configuration context (redact sensitive identifiers).
  • Original event messages and timestamps.
  • Reporting source and collection method.
  • Workload and observed service impact.
  • Expected behavior and applicable documentation.
  • Hypotheses, gaps and planned next actions.
